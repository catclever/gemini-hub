# 远端红心状态查询与缓存设计模式

### 背景与痛点
在目前的 `jsososo/QQMusicApi` 甚至部分网易云 API 体系中，通常**没有**提供类似 `/is_liked?songid=xxx` 这样轻量级的“查询单首歌曲是否被喜欢”的接口。
如果每次切歌时，都去远端进行查询，会面临：
1. **找不到专用接口**：只能通过拉取整份红心歌单来比对。
2. **性能与风控开销大**：红心歌单通常包含几百到几千首歌，每次切歌全量拉取极大地浪费网络资源，且极易触发平台的反爬（风控）机制，导致 IP 被封或接口返回 `301` / `403`。

### 标准获取流程 (QQ音乐示例)
要判断一首歌是不是在红心列表里，标准流程为：
1. 调用 `/user/songlist?id={QQ号}` 获取该用户的所有歌单。
2. 找到其中 `dirid === 201` 的歌单，这就是系统固定的“我喜欢”歌单，提取出它的 `tid`（即实际的歌单 ID）。
3. 调用 `/songlist?id={tid}` 全量拉取“我喜欢”的歌单详情。
4. 遍历返回的 `songlist` 列表，提取歌曲的 `songmid` 或 `songid`，判断当前歌曲是否在其中。

*(网易云稍有不同，直接提供了一个 `/likelist?uid={uid}` 接口返回全量喜欢的纯 ID 数组，省去了查询歌单详情的步骤，但原理相同。)*

### 内存 Set 缓存优化 (最佳实践)
为了解决切歌频繁查状态的痛点，最佳的工程实践是：**仅获取一次，全局在内存中维护一个 Set 进行 O(1) 级比对**。

1. **单次全量拉取**：在软件启动，或本会话首次需要判断状态时，全量拉取一次喜欢的歌曲 ID/MID。
2. **存入内存 Set**：将获取到的所有标识符存入本地的 `Set` 集合（如 `myFavSet`）中。
3. **极速状态比对**：后续每次切歌，直接通过本地进行极速的 O(1) 判断：`myFavSet.has(currentSongId)`。
4. **状态增量同步**：当用户在界面上手动点击“红心”（收藏/取消收藏）时：
   - 发送请求给云端 API 执行实际操作。
   - 请求成功后，同步使用 `add()` 或 `delete()` 更新本地的 `myFavSet` 集合。
   这样即可保证接下来的比对依然是准确的，且完全不需要重新去远端全量拉取歌单。
