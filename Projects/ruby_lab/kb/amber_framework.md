# Amber Framework & Environment

## 1. Overview
Amber is a concurrent backward-chaining rule engine based on static graph analysis, located at `/Users/kael/workbench/ruby_lab/amber`.
It allows defining business rules with implicit dependencies and resolves them concurrently using backward-chaining and strategy priority evaluation.

> [!NOTE]
> An experimental "Amber 2.0 (Reactive State Machine)" draft generated by an autonomous agent on PVE has been safely archived in the git branch `archive/amber-2.0-draft`. The active `main` branch maintains pure Amber 1.0 rule engine architecture.

## 2. Environment Specifications
- **Ruby Runtime**: Ruby 3.3.0 managed via `mise`.
- **Bundler**: Bundler 2.5.3.
- **Isolation**: Independent git repository within the `ruby_lab` multi-repo workspace.

## 3. Core Architecture Map (Amber 1.0)
- `Amber::Rules` (`lib/amber/rules.rb`):
  - Stores rule strategies: `{ key => [ { deps: [...], block: Proc } ] }`.
  - Uses `Amber::DependencySpy` (a `BasicObject` spy) during boot-time dry run to automatically infer dependencies without executing runtime side effects.
  - Cycle detection via `Amber::DependencyAnalysis.check_cycles!`.
  - DOT graph visualization via `Amber::DependencyAnalysis.to_dot`.
- `Amber::Engine` (`lib/amber/engine.rb`):
  - Concurrently resolves target goals (`resolve(target)`) via `Concurrent::Promise`.
  - Strategy racing: evaluates all matching strategies for a key in parallel, filters skips/rejections, and selects highest priority outcome via `emit(value, priority: N)`.
  - Detects ambiguous results when multiple strategies at the highest priority return different values.
  - `ExecutionContext` handles runtime dependency lookup with lazy resolution on conditional branches (`method_missing`).
- `Amber::Result` (`lib/amber/result.rb`): Encapsulates computation outcome with priority.
- `Amber::Failure` (`lib/amber/failure.rb`): Explicit rule rejection mechanism for audit logging.
